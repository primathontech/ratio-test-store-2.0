# Common Sections — extraction playbook

How a section from a source theme becomes a portable, editor-ready package in
this library. Reference implementation: [`Hero/`](./Hero). Keep this file free
of source-theme names — provenance lives in the team's local extraction docs.

## The package (one folder = the unit of distribution)

```
common/<Section>/
├── contract.ts      settings schema (= editor form) + testIds + acceptedBlocks
│                    + data declaration + <Section>VM type      (stable spine)
├── logic.ts         build<Section>VM(data, settings) → VM — pure, server-safe;
│                    stateful sections ALSO export useSectionLogic (wraps it)
├── coverage.ts      every variant-native settings key classified shared /
│                    passthrough / generated — `satisfies Record<keyof …>`
│                    makes tsc name any unclassified key
├── metadata.ts      per-variant tags (industries/vibes/goals/density/pages)
│                    + preview_image — feeds the editor picker + AI generator
├── variants.ts      { v1..vN, default } — variants receive ONLY the VM
├── V1/ V2/ …        one folder per look; its types.ts = the vm.vN extension,
│                    its sample-data.ts = the curated zero-settings look
│                    (settings → data → sample fall-through — EVERY variant
│                    must look great with no configuration)
├── _shared/         section-internal building blocks (promote to
│                    common/primitives/ when a 2nd section needs them)
├── i18n/en.json     canonical strings (the editor preset imports from here)
├── preview/         one image per variant (800px wide)
└── defaults.ts      seeds the palette preset — real values, not blanks
```

App-side there are only thin pointers: the editor preset folder
(`editor-integration/sections/common/<kebab>/` — generated by the scaffolder)
and one-line entries in `widget-registry.ts` + `available-sections-registry.ts`.

## Extraction steps

1. **Fetch** each source theme's implementation of the section into a scratch
   dir (never into the repo). Record which theme produced which variant in the
   local extraction-matrix doc — not in code, not in this file.
2. **Normalize** — neutralize every identifier (`cs-<name>-v*` CSS prefixes, no
   theme names anywhere); re-theme hardcoded colors onto the generic scheme
   token contract (`Hero/_shared/scheme-vars.ts`; library defaults ship in
   `Hero/_shared/tokens.css`); convert block systems to the flat
   type-discriminated objectArray; inventory each look's native settings.
3. **Scaffold** — `bun run create:section <Name>`, then port each look as
   `V{n}`: its native settings interface goes in `V{n}/types.ts` verbatim and
   becomes the typed VM extension.
4. **Map** — fill `logic.ts` (shared semantics + per-variant extension
   builders) and `contract.ts` fields; classify every key in `coverage.ts`
   until tsc is green. Promotion rule: a field ≥2 variants use → shared
   contract field; everything else stays native passthrough.
5. **Tag** — `metadata.ts` per variant + `preview/` image per variant (copy the
   lead image to `public/common/section-previews/<kebab>.png` for the palette).
   Capture with **Playwright** (headless-Chrome `--screenshot` can skip webfont
   text) against a throwaway route that renders the widget at zero settings —
   that same route doubles as the "looks great by default" check.
6. **Verify** — the battery below, then editor sign-off.

## Definition of done (per section)

1. **Render proof** — SSR probes on the demo route: every shared field
   exercised in the template asserts a DOM/CSS effect.
2. **Editor proof** — palette add → sidebar shows real defaults → edit ≥3
   fields incl. variant switch → visible change.
3. **Portability proof** — `cp -R` the folder into a sibling app → `generate`
   → renders with zero edits.
4. **Fidelity proof** — per-variant screenshot vs the source look.

Gates that enforce the shape (pre-commit): tsc (coverage completeness, VM
seam, metadata enums) · `check:parity` (coverage.ts/metadata.ts/preview exist)
· read-only guard (merchant forks can't edit common/) · no-theme-names grep.

## Merchant customization (never fork a section)

Tokens → settings → blocks → variant pick → **logic-wrap** (dev): a fork
decorates the section's logic without touching common/ —

```ts
// widgets/local/<Section>/logic.ts (merchant fork)
import { buildCollectionGridVM } from "@/widgets/common/CollectionGrid/logic";
export const buildVM: typeof buildCollectionGridVM = (data, settings) => {
  const vm = buildCollectionGridVM(data, settings);
  return { ...vm /* decorate vm.shared handlers/fields here */ };
};
```

…registered in `widgets/_overrides.ts` (see its doc comment). One wrapper
covers all variants. UI-level alternative: slot/primitive override in
`local/primitives/`.

## Traps (do not rediscover these)

- The editor sidebar shows **stored values, not schema defaults** — seed real
  values via `defaults.ts`, and delete+re-add stale sections after contract
  changes.
- DynamicForm has **no conditional fields, no grouping, no color input** —
  colors are hex text fields; variant-scoped fields carry a label hint.
- Editor image settings arrive as **`{src, alt}` objects** — normalize before
  `next/image` or the whole page error-boundaries.
- Dev chunks must **never be cached immutable** (`bootstrap/next-config.js` is
  dev-aware; a year-cached stale chunk makes every fix invisible).
- **Click-probe every interactive element** during extraction — disclosure
  toggles can reveal content that belongs inside the section's scope.
- Scheme tokens: variants read generic `--color-*` vars only; hosts without
  theme.json schemes fall back to the library defaults shipped in the folder.
